# Harness 工程：把模型的一次决定变成世界上的一个动作

这是一份 harness 工程的长文笔记。它不假设你读过任何课程，也不需要你先了解 Codex。读完之后，你应该能独立回答这样的问题：给定一个新的 agent 需求——"要支持定时跑""窗口不够了""要能同时改两个模块""外部系统的能力怎么接进来"——它的本质约束是什么，有哪几种可行解法，每种在什么维度上崩掉，你选哪个，代价是什么。

Codex 在这份笔记里的角色是一个可考证的工业样本，不是标准答案。凡是提到它的地方，给的是"有人在生产里押过这个注"这一条证据，以及"它为此付了什么价"。凡是某个做法只在教学实现里存在、真实产品并没有，都会就地说明，免得你把一套演示用的 API 当成行业惯例。

版本锚点：文中关于 Codex 的具体键名、命令名和枚举值，对照的是 2026 年初 `openai/codex` 主干（Rust 实现在 `codex-rs` 下）与 v0.144.x 的 CLI。这些名字的变动速度比设计原则快得多，后面会看到好几处版本漂移的例子——那本身就是一条值得记住的经验。

## 第 0 部分 · 这套东西是什么

### 0.1 落差在哪里

大模型的输出只有一种形态：一段文本。哪怕它说"我现在要运行 `npm test`"，说完也就结束了——它不会真的去跑，看不到输出，更没法基于输出继续推理。你可以手动把命令粘进终端，再把结果粘回对话框，让它接着干；下一条命令出来，你再跑一遍，再粘一遍。

这中间的每一个来回，都是一个人在当胶水层。把这层胶水自动化，就是 harness 的全部工作：模型决定做什么，harness 去执行，把结果喂回去，重复，直到模型不再要求做任何事。

写成一行代码大概三十行就够了。但这三十行跑在真实的机器上、真实的代码仓库里、真实的一个小时长的任务上时，会在每一个方向上碎掉：

命令会毁掉不该毁的文件。上下文会在第四十轮塞满，API 开始拒绝请求。进程崩了，一小时的工作没有任何记录。API 返回 429，循环整个退出。`npm install` 跑了三分钟，这三分钟里模型在按秒计费地空转。两个并行的任务改同一个文件，互相覆盖。模型在第三步忘了第一步说过"不要动 lock 文件"。

harness 工程要做的，就是把这些逐一变成设计好的、可解释的行为。它不是 prompt 工程——提示词写得再好，也不能阻止一条被批准的命令删掉磁盘。它也不是"把一堆工具函数堆进聊天机器人"——那解决的是能力问题，不是运行时问题。它是一套运行时：**在模型的一次决定和世界上真实发生的一个动作之间，插入一层可恢复、可审计、可限权的机制。**

把这件事拆成可检验的能力项，大概是五条：

第一，能画出这个运行时的完整状态机，包括所有分支——正常收尾、审批拒绝、沙箱越界、压缩触发、限流退避、用户中止、慢命令 yield、子执行者派生。少画一条，线上就会在那条路上出事。

第二，拿到一个新机制，能说出它该挂在哪里，以及为什么不挂在别处。挂错地方的后果高度一致：要么去改主循环，要么把策略写进提示词，要么让模型自己声明它很安全。

第三，能把纠缠在一起的东西拆成互相独立的轴。信任是一个轴还是两个轴，注意力和寿命是不是一回事，隔离有几个级别——分不清，配置项就会互相打架。

第四，把所有的拒绝、失败、越界、超时都当成数据，而不是异常出口。一个成熟 harness 的失败路径设计精度，不应该低于成功路径。

第五，知道每个机制的代价，并且能说出什么场景下不该用它。

### 0.2 三条贯穿始终的约束

后面所有的设计，都在这三条之下。它们不是格言，是可以用来否决方案的判据。

**循环不改形状。** 加一个新机制，是在既有的固定位置上挂一个钩子，不是另写一套控制流。判断标准很硬：如果新需求让你想在主循环里加一个 `if`，八成是挂错了地方。这条约束的价值在扩张期才显现——加第二个机制和加第二十个机制的难度应该差不多。

**决策权和执行权分离。** 模型产出的是结构化的意图信号；harness 负责执行、拦截、记录。模型对自己动作的风险评估不具备任何权威性——它会误判，会被读进来的内容带偏，会对含糊指令做激进解读。所以"这次能不能做"这个问题，必须由 harness 回答，而且回答的依据不能是模型的自我申报。

**看见不等于强制。** 这条最容易被忽略。让 harness"知道"模型的计划，和让 harness"能拒绝"模型的非法动作，是两种完全不同的能力，需要两套完全不同的机制。把可见性机制当成约束机制用，是 agent 系统里最常见的一类安全错觉。

### 0.3 全景

![Agent Loop 运行时全景](./assets/panorama.svg)

这张图是全文的索引。最外层是那个循环，所有机制都是它路径上的守卫、分流或者外套。虚线框在循环外面——它们能把工作交进来，但不属于循环本身。

先读一遍它的骨架，细节后面每一节展开：

一次运行的入口可以是人敲的一句话，可以是定时器到点新开的一条空白线程，可以是定时器追加回一条旧线程，也可以是某个执行者派生出来的一份干净输入。循环本身不关心自己是被谁叫醒的。

进循环之后，第一件事不是调模型，而是估算当前这段上下文还剩多少余量。逼近预算就先把旧历史压成一段摘要，腾出空间，再发请求。

调模型这一步外面包着错误分类：限流退避，超长压缩后重试一次，用户中止立刻停但保住会话，未知错误少量重试后放弃。

模型返回之后，整段原样追加进那条唯一的输入序列，同时写进磁盘上的只追加日志。

然后是唯一的分支判据：这一轮里有没有工具调用。没有，抽出最终文本，收尾退出。有，按工具的身份分流——改 harness 内部状态的走内部路径，派生子执行者的走子循环，慢命令走 yield 窗口，外部服务走协议桥，会碰到真实世界的那些，要先过一条判定链才允许落地。

任何一层说"不"——审批拒绝、沙箱越界、能力未开启、依赖未就绪、工具名不存在——都写成一条普通的工具结果喂回去，循环继续。只有用户主动中止是一等的出口。

## 第 1 部分 · 内核：把决定变成动作

### 1.1 循环本身：停止判据为什么必须是结构信号

最小可运行的 agent 只需要一个循环和一个工具。把用户的话作为第一条输入，连同工具清单发给模型；模型返回的东西整段追加进输入序列；检查里面有没有工具调用；有就执行、把结果追加回去、回到开头；没有就打印最终文本、退出。

这三十行不是智能本身，它是让模型能够持续行动的最小框架。后面所有的机制都叠在它上面，而它本身从头到尾不变。

值得单独推敲的是"什么时候停"这个判据。表面上有三种做法：

**读懂模型说了什么。** 让 harness 解析最终文本，判断它是不是表达了"我做完了"。这条路在演示里能跑通，在生产里必然出事。自然语言的边界情况是无限的："我先看一下这个文件"到底是完成还是没完成？"如果你需要我继续请告诉我"算不算终态？每补一条规则都会引入新的误判，而误判的代价是循环该停的时候不停、该继续的时候停了。

**让模型显式声明终止。** 给模型一个 `finish` 工具，调用它才算结束。这比解析文本强，但引入一个新的失败模式：模型忘了调。忘了调的后果是循环空转——模型没有工具要调，也没有宣布结束，harness 不知道该干什么。你还得为"既没有工具调用也没有 finish"这种情况再设计一条兜底路径，等于绕回原点。

**看这一轮的输出里有没有工具调用。** 有就继续，没有就结束。这条判据不理解任何语义，它只看一个结构事实。它的边界情况是有限且可枚举的，因为"有没有函数调用项"这件事本身没有歧义。

第三种是对的，原因不在于它更聪明，而在于**它的判据落在结构上而不是语义上**。这是 harness 设计里反复出现的一个模式：只要一个判断可以从结构里读出来，就不要让它依赖对内容的理解。理解内容的地方是模型，判断结构的地方是 harness，这条分工线不该模糊。

循环里的状态也只有一份：一条只增长的输入序列。模型每一轮的完整输出——推理过程、要说的话、工具调用——都原样追加进去，一个字节都不改。

这一点在实现时很容易被破坏。看到模型的推理过程占了很多 token，想裁掉；看到工具输出很长，想截断；看到某些项"没什么用"，想过滤。这些都会让模型接不上自己上一轮的判断——它在第三轮引用的是自己第二轮的推理，而那段推理已经被你删了。后面所有关于上下文的机制，压缩也好、持久化也好、审批拦截也好，本质上都是在做"往这条序列里追加什么、什么时候追加"的文章，没有一个会去改写已经在里面的内容。

生产实现和这个最小版本有一个重要差别：它消费的是事件流，不是一整轮的返回值。模型边生成边吐出 item，harness 一看到一个完整的工具调用就可以立刻派发，不必等整轮文本生成完。这带来的好处是只读调用能更早并行起跑；带来的复杂度是"什么时候算失败"变得更微妙——连接可能在流中途断开，你得判断已经吐出来的部分能不能续上，还是必须整轮重来。

Codex 的这层循环在 `codex-core` 这个 crate 里，函数叫 `run_turn`；上面套着几种不同的任务类型——常规回合、压缩回合、审查回合——它们驱动的是同一个 `run_turn`。这个结构本身说明了一件事：压缩和审查在它的设计里不是主循环的分支，而是主循环的另一种调用者。

### 1.2 工具契约：从一个 shell 到一张注册表

只给模型一个 `shell`，它理论上什么都能干：读文件拼 `cat`，写文件拼重定向，改一行拼 `sed -i`，找文件拼 `find`。看起来很优雅，一个工具解决所有问题。

实际上这一层翻译是纯亏损，亏在四个地方。

模型脑子里的意图是"读 `src/auth.ts` 的前一百行"，它必须先把这个意图编码成一个 shell 字符串。这一步会出错——引号嵌套、路径里的空格、特殊字符转义，全是经典坑。它还费 token。

harness 收到的是一团不透明的字符串。执行之前，它没有办法做任何类型校验，也没有办法知道这条命令会碰哪些路径。后面想加审批、加沙箱，第一步就卡住了：你连"这条命令要写哪个文件"都不知道，怎么判断它越没越界？

输出也是自由文本。`ls` 的输出格式随平台变，随参数变，模型得自己解析。

最后，模型一轮里想做几件互相独立的事——读 A、读 B、看一眼目录——被迫串成几条 shell 命令，或者用 `&&` 拼成一条，失去了并行的可能。

解法是让每一种能力本身成为一份结构化契约。给模型的清单上，每个工具是一条带类型参数的 schema，模型填参数而不是拼字符串。harness 这边维护一张从工具名到处理函数的映射表，收到调用就查表执行，查不到就返回一条明确的错误而不是崩溃。

这样做之后，扩张的代价变成常数：加一个工具，改两个地方——清单里加一条 schema，映射表里加一行。循环一动不动。**判断一套工具系统设计得好不好，最简单的标准就是这个：加第二十个工具如果明显比加第二个难，说明分发逻辑里混进了不该有的特殊情况。**

这里有一个刻意的设计决定值得点出来：**分发表只回答"调哪个函数、传什么参数"，不回答"这次能不能做"。** 把权限判断塞进分发表是很有诱惑力的——反正都要在这里过一遍。但那会让两件事永久耦合：以后想换一套权限策略，得改分发；想加一个不需要权限的工具，得在分发里写例外。权限判断应该是包在分发外面的一层，这个分层后面第 2 部分会展开。

分发按名字查表、彼此无状态，所以同一轮里互相独立的调用天然可以并行执行。这不是额外设计出来的能力，是结构化调用的副产品。

`shell` 本身不该被删掉，它是逃生舱——总有一些事情没有对应的专用工具。但它从"唯一的工具"变成"兜底的工具"，这个地位变化很关键。

### 1.3 改文件为什么值得单独设计

在所有工具里，"修改文件"这一类值得单独拿出来推敲，因为它是唯一一个会让工作区进入损坏中间态的动作。

给模型改文件的能力，有三种做法：

**让它生成 `sed` 之类的命令。** 最省事，但改动的真实效果要等命令跑完才知道。正则写错了，可能把文件里所有匹配都替换掉，而模型只想改第一处。改坏之后，工作区处于一个模型和人都不清楚的状态。

**让它输出整份新文件。** 这条路避开了正则的坑，但代价很大：改一行要重写整个文件，费 token 且容易在重写过程中丢掉无关的部分（模型"顺手"改了别的地方是很常见的）。多文件修改时，写到第三个文件失败了，前两个已经落盘，工作区停在改了一半的状态。

**结构化补丁。** 模型声明改哪个文件、锚定哪一段上下文、删哪几行、加哪几行。这条路有三个具体收益：

可审查性。补丁本身就是一份 diff，人和 harness 都能在执行前看清它要做什么。这也是后面审批环节能展示有意义信息的前提——给人看一条 `sed` 命令让他判断风险是不现实的，给人看一份 diff 就现实。

原子性。先把整个补丁解析完，在内存里算出每个文件的最终形态，全部校验通过才落盘。任何一个文件的上下文对不上，整个补丁被拒绝，磁盘上一个字节都不动。工作区要么是全新状态，要么是原状态，没有中间态。

失败可恢复。每一段修改都要先在文件当前内容里找到声明的上下文才替换。找不到就返回一条精确的错误——哪个文件、哪一段没匹配上。模型下一轮拿着这条错误去重试，而不是对着一个已经被改坏的文件发呆。

**失败路径的设计精度不该低于成功路径**，这一条在补丁工具上体现得最明显。返回"补丁应用失败"和返回"`src/auth.ts` 第 42 行附近的上下文没匹配上，当前内容是……"，对模型下一轮的修正能力差别巨大。

补丁还有一个暴露方式上的选择。作为普通的函数工具，补丁内容是一个 JSON 字符串参数——外层 JSON 合法性有保证，但补丁体本身可以是任意字符串，格式错误只能靠解析器事后兜底。另一种方式是让模型直接输出一段受文法约束的原始文本，语法在生成阶段就被限制，模型在结构上产不出非法补丁。后者更强，但要求你能控制模型侧的解码过程——不是所有部署形态都有这个条件。Codex 早期用一个特性开关控制这两种形态，现在文法约束的那种已经成为默认行为，开关被移除了。

### 1.4 工具箱的边界：三种执行位置

![工具注册表与三种执行位置](./assets/tool-registry.svg)

把工具做成注册表之后，一个自然的问题是：这张表里能装什么？

如果只装"读文件、写文件、跑命令"，模型能做的事就锁死在当前工作目录里。真实任务经常要越过这条线：回答"这个库最新版本改了什么"需要联网；"照这张截图做 UI"需要模型真的看见图片；"打开这个页面把 API 签名抄下来"需要驱动浏览器。

有意思的是，加这些能力**完全不需要改动分发逻辑**。对模型来说它们长得一模一样：一个名字、一份参数 schema、一次调用。变的只有一件事——这个工具真正在哪里执行。这可以分成三类，而这个分类直接影响你后面怎么给它们套安全策略：

| 执行位置 | 例子 | 副作用落在哪 | 安全策略怎么套 |
|---|---|---|---|
| 本机 | 跑命令、读写文件、读取本地图片 | 你的文件系统与进程 | 完整走审批与沙箱 |
| 服务端托管 | 联网搜索、图片生成 | 不落在你的机器上 | 不需要逐次审批；风险在"读进来的内容可能是恶意的" |
| 驱动外部目标 | 控制浏览器、控制桌面 GUI | 落在被驱动的那个目标上 | 沙箱管不到；需要独立的一套来源/权限策略 |

第二类和第三类是很多人漏掉的。托管工具不消耗你机器上的任何东西，所以逐次审批没有意义，通常靠一个开关一次性启用。但它引入了另一类风险：搜索回来的网页内容会进入模型的上下文，而那是外部可控的文本——提示词注入的主要入口之一。Codex 对此的处理很能说明问题：它的联网搜索默认走一个自己维护的索引（缓存态），而不是实时抓取，显式开启才会去发真实请求。降低的正是这个暴露面。

第三类更麻烦。驱动浏览器意味着 harness 亲自去操作一个外部程序，文件沙箱对它一点约束力都没有。所以它需要自己的一套策略维度——允许访问哪些站点、能不能上传下载、能不能拿到完整的调试协议权限。这是一个独立的权限空间，不能挂在文件沙箱那套档位上。

**加能力的时候要问的不是"这个工具好不好用"，而是"它的副作用落在哪、现有的哪道门管得住它"。** 管不住，就说明需要新开一条策略维度，而不是把它硬塞进已有的档位里。

哪些工具被注册进表里，通常由一组特性开关决定。这是一个值得抄的模式：能力的装配发生在启动时，由配置驱动，而不是写死在代码里。它让"这个部署形态支持哪些能力"变成一个可配置的事实，也让实验性能力有地方待着——分阶段标记（稳定、实验、开发中、已弃用、已移除）比一个布尔开关能表达多得多的信息。

### 1.5 模型后端是一个可替换的旋钮

到这里为止，有一个隐含前提一直没被动过：模型住在某个特定的云服务上。

真实场景经常要拆掉这个前提。有人想用本机跑的开源模型，代码不出机器也不付 API 费用。有人公司统一架了一条网关，所有流量、审计、计费都得从那里过。有人要接一个自托管的兼容端点。

关键在于认清这是哪一层的问题。循环本身对此毫不关心——它只要求"把我这份输入交出去，把输出项拿回来"。所以这不是循环的问题，是循环底下那层传输的问题。

把模型后端抽象出来，需要三个正交的旋钮：

**指向谁。** 一个基础 URL。本机的推理服务、公司网关、第三方端点，区别只是这个字符串。

**用什么凭证。** 一个环境变量名，而不是凭证本身。这个间接层很重要：配置文件会被提交、会被分享，凭证不该出现在里面。本机服务通常连凭证都不需要。

**讲哪种线路协议。** 不同的后端可能讲不同的 HTTP 方言——请求体的形状、工具调用怎么表达、流式事件怎么切分，都不一样。这需要一个适配层，而**这个适配层必须是系统里唯一知道方言差异的地方**。一旦方言的判断逻辑渗进了循环或者工具分发，换后端就变成一次全局手术。

这里有一个真实的演化很值得看。Codex 的配置里有一个协议选择项，历史上有两个取值：新的响应式协议和旧的对话补全协议。现在它只剩一个值了——旧的那个被移除，配了会直接报错并告诉你怎么改。本机推理服务也相应地都加上了新协议的端点支持。

这个收敛说明了一件事：**维护两套方言适配是有持续成本的，而这个成本会随着协议本身的演进不断上升。**当新协议引入了旧协议表达不了的东西（比如推理过程项、更细的流式事件类型），适配层就得开始做有损翻译，而有损翻译的 bug 极难排查。与其如此，不如砍掉一边，把翻译的责任推给外部代理——想接只讲旧协议的后端，在前面架一个翻译代理去。

这是一个可迁移的判断：**适配层该支持几种方言，取决于你能不能承受它们长期发散。**两种协议如果都在活跃演进，适配层会成为最脆的一块。

还有一个边界值得注意：这类"模型后端指向谁"的配置，属于机器级决定，不该让项目级的配置文件覆盖。否则一个克隆下来的仓库就能把你的模型流量指向别处。后面讲配置解析时会看到，这类"信任有边界"的约束是配置系统里必须显式设计的部分。

## 第 2 部分 · 信任：谁允许它动手

### 2.1 两道正交的门

工具能跑了，下一个问题是：凭什么允许它跑。

先排除一个方案：靠提示词约束。"不要删除文件""危险操作前先确认"这类话写进系统提示，能降低概率，但不构成边界。模型会误判，会被读进上下文的内容带偏（一个 README 里写着"运行 `rm -rf` 清理缓存"就够了），会对含糊的指令做激进解读。**任何一条你不能接受被违反的规则，都不能只存在于提示词里。**

真正的边界必须写在 harness 里。而这里最关键的一步，是认清这其实是两个不同的问题，需要两道不同的门：

**这一下要不要先问人？** 这是审批。
**这一下物理上碰得到什么？** 这是沙箱。

![审批与沙箱是两道正交的门](./assets/trust-axes.svg)

把它们焊成一道闸，会同时失去两种调节能力，而且是两个方向的失败：

只做审批，不做沙箱。那么每次批准都是无限授权——你点了 `y`，命令就以你的全部用户权限跑在真实文件系统上。一个被批准的删除命令照样能清空磁盘。更要命的是，"这个路径在不在工作区内"这种判断只能靠人一条条看。人会手滑，会疲惫，会在第五十次弹窗时下意识按回车。**把边界押在人的注意力上，就是没有边界。**

只做沙箱，不做审批。那么笼子里的危险动作全都拦不住。删掉整个 `build` 目录、强制推送、重置未提交的改动——这些路径全在可写范围内，沙箱没有任何理由拒绝。沙箱回答的是"能碰到哪"，不是"该不该碰"。

所以必须是两道。它们各自需要的东西也不一样：

审批需要的是**可调节的信任档位**，因为使用场景差异极大。有人在自己的实验仓库里希望它全自动跑，有人在生产代码库里希望每一次写入都过目。常见的档位设计大概是这几种语义：从不问；只有危险动作才问；由模型判断什么时候该问；除了已知安全的只读命令以外都问。风险分类由 harness 自己做——**绝不信任模型的自我申报**，因为那正是需要被约束的那一方。

被拒绝的调用不是崩溃。harness 把一条"这次调用被拒绝了"的错误写成普通的工具结果喂回去，模型读到之后换一条更安全的路线，循环继续。这一点很重要：审批是一次对话，不是一堵墙。

沙箱需要的是**机器强制的硬边界**，而且要包住每一次落地执行，包括那些看起来"只是在项目里改个文件"的。它的档位画的是笼子的可写范围：什么都不能写；只能写工作目录；完全不设限。网络通常是同一个笼子的另一条边——工作目录可写档下默认禁网是个合理的默认值，因为它堵住了"把代码传出去"这条路。

关于沙箱有一个常见误解要澄清：它**不是**"先在副本上改，确认没问题再同步回来"。命令写的就是真实文件，沙箱只是一个套在这条进程上的笼子。工作目录可写档的含义是"笼子的可写根设成了启动目录"，屋里的改动当场落盘。

强制力从哪来，决定了这道门是真是假。用户态的路径字符串检查能演示思路，但它依赖"harness 记得去检查"——漏一条代码路径就漏一个洞，而且命令跑起来之后可以做任何事（比如它自己 fork 一个子进程）。真正的强制力来自操作系统内核。Codex 在 macOS 上用系统自带的沙箱框架，在 Linux 上现在默认用 bubblewrap 做文件系统隔离，再叠上 seccomp 过滤网络和禁止提权，Windows 上有原生的沙箱实现。**边界一旦依赖应用层记得检查，它就不是硬边界。**

顺带记下一处版本漂移，因为它本身是个有用的教训：Linux 侧早期用的是内核的 Landlock 机制，现在成了 legacy 选项，而且对某些策略直接被拒绝——因为它隔离不了 Unix socket，而 harness 自己就在用 Unix socket 对外提供服务。**沙箱后端的选择会被 harness 自身架构的演进反过来推翻**，这不是能一次选对的决定。

最后是两道门的实际配合顺序。分开讲是为了职责清晰，落地时它们是拧在一起的：命令先按当前沙箱档位在受限环境里跑；如果它因为需要更高权限而失败（要写笼子外面、要联网），并且审批策略允许问人，这时才弹出审批，批准之后用提升的权限重跑。所以那个"失败后才问"的审批档位，它说的"失败"很多时候就是"沙箱拦住了"。

记住顺序：**先关进笼子，再决定要不要放出来。**不是"区内走审批、区外走沙箱"。

### 2.2 安全是一条判定链，不是一个开关

![一个动作的安全判定链](./assets/safety-gates.svg)

两道门讲清楚之后，把视角拉远一点会发现，真实系统里"这个动作能不能跑"要经过的关卡远不止两道。自治程度不是一个布尔值，是一个刻度盘；而刻度盘的实现，是一条有固定顺序的判定链。

Codex 里这条链大致是五道闸，顺序如下。顺序本身比每一道闸的内容更值得学：

**第一道，配置代码的信任。** 如果这个动作来自一段用户配置的钩子脚本，先问这段代码可不可信——项目本身被标记为可信，或者这条钩子被单独授过信，才允许执行。理由是钩子是从配置文件里读出来的代码，一个克隆下来的仓库可以带一段钩子进来。这道闸排第一，是因为它管的是"这段逻辑本身要不要执行"，比它要做什么更基础。

**第二道，能力是否启用。** 这个动作依赖的特性开着吗？关着就直接拒绝。排在沙箱前面的理由很直白：能力都没开，根本轮不到讨论它在哪跑。

**第三道，总旁路。** 有一个显式的、名字里带"危险"的开关，设了就直接放行，短路掉后面所有的闸。它存在的意义就是短路，所以必须排在被短路的东西前面。

**第四道，沙箱。** 物理边界。越界的写入连问都不必问，直接拒绝。

**第五道，审批与信任。** 决定一个本来能跑的动作，要不要再升级给人确认。

最后还有两枚"保险丝"钉在整条链的末尾：一道额外的独立复审层，和"这个项目被标记为不可信"这个事实。它们的作用是单向的——只能把已经是"放行"的风险动作扳回"询问"，不能反过来把"拒绝"变成"放行"。这个单向性是刻意的：安全机制的叠加必须是单调收紧的，任何一个能放松其他机制的开关，都会让整个链条的行为难以推理。

最终合成出来的是三值，不是两值：**放行**（直接执行）、**询问**（升级给人）、**拒绝**（连问都不必问）。三值比两值好在哪？好在"拒绝"和"询问"的区别被保留了下来。物理上越界的写入和策略上需要确认的写入，对用户是两种完全不同的信息——前者告诉你"这条路走不通，换个思路"，后者告诉你"要不要让它这么干"。压成两值就丢了这个区别，用户会在一堆弹窗里失去判断力。

这条链里最值得抄的设计是那个总旁路开关。它的存在承认了一个现实：有些环境本身已经是隔离的——一次性容器、CI runner、云端执行环境——在里面再套一层沙箱是纯开销。所以提供一个显式的、名字足够吓人的开关是对的。但它有两个设计细节值得注意：一是名字，全名长得让人不可能手滑输进去，而且文档明确写着唯一合法用途是"环境本身已经被外部隔离"；二是它的位置，排在链条前部短路后面所有东西，这意味着它的语义是干净的——设了就是全放行，不存在"设了但某些情况下还是会拦"这种半吊子状态。

**给危险的东西一个显式的、丑陋的、语义干净的开关，好过让用户用一堆小开关拼出同样的效果。**后者会让人在不理解全局的情况下意外达到全放行状态。

最后记一处版本漂移，它是个典型的教训。前面讲审批档位时提到的四档语义——从不问、失败才问、按需问、除了已知安全都问——在较早的 Codex 版本里确实是四个枚举值。现在其中两个没了：最严格的那档被移除，"失败才问"被标记为弃用并变成"按需问"的别名，同时新增了一种细粒度配置形态，可以分别设置沙箱升级、规则、技能调用各自的审批方式。

**枚举值会收敛，也会展开。** 你该记住的是这条轴上有哪些语义位置，以及它们各自解决什么问题；不该记的是某一版里它们叫什么名字。面试里说"审批策略有四档分别叫什么"是背诵，说"审批这条轴需要覆盖从全自动到全确认之间的哪几个语义位置、为什么粗粒度枚举后来会演化成细粒度配置"才是理解。

## 第 3 部分 · 注意力：窗口是稀缺资源

上下文窗口有限，这件事在长任务里会以四种完全不同的方式咬你：计划只存在模型脑子里，做着做着跑偏；一条支线的几十轮中间过程淹没了主线；项目规范一次性塞进系统提示，每轮都在烧无关 token；历史只增不减，直到 API 拒绝下一轮请求。

![注意力预算的四条路径](./assets/attention.svg)

这四件事看起来都是"上下文不够用"，但成本结构完全不同，所以解法也不同。用同一招（比如"写一个更好的系统提示"）去解，只会把真正有效的指令稀释在噪音里。下面按成本结构分开讲。

### 3.1 外化计划：只换能见度

给 agent 一个十步的重构任务，它做到第三步就开始即兴发挥——因为第四到第十步早就被前三步产生的工具输出挤出了注意力。

问题不在模型不会拆任务，在于**拆解的结果只存在于模型内部**。harness 看不见它，所以在跑偏的时候没有任何抓手。

解法是给模型一个专门用来声明计划的工具。它不做任何实际工作——不能读文件，不能跑命令。它唯一的作用是把计划从模型内部搬到 harness 里。动手之前先声明整份步骤列表，之后每有进展就重新声明一次。

这里有几个具体的设计决定：

**整体替换，不做增量合并。** 模型每次发的是完整的列表，harness 收到就整体替换掉旧的。这看起来浪费 token，但避免了一整类问题：增量更新需要模型准确引用步骤 id，需要 harness 处理"引用了不存在的步骤""同一步被更新两次""删除了正在进行的步骤"这些情况。整体替换把所有这些变成不可能状态。**用一点冗余换掉一整类状态同步 bug，在 agent 系统里几乎总是划算的**，因为模型产出的引用天然不可靠。

**状态只有三个，同一时刻只允许一步进行中。** 三个状态是待办、进行中、已完成。"只允许一个进行中"这条约束不是为了好看——它逼着模型在每一步开始前做一次显式的选择，而这个选择对 harness 是可见的。允许多个并行进行中，这份清单就退化成了一个待办事项集合，看不出模型现在到底在干什么。

**它走 harness 内部路径，不进沙箱也不过审批。** 因为它不碰任何外部世界。这也是前面说的"分发表只回答调哪个函数"那条设计的好处——工具的身份决定了它走哪条路径，不需要在权限层里为它写例外。

现在说最重要的一点，也是这一节真正的价值所在：**这个机制增加的是可见性，不是约束力。**

模型完全可以声明一份漂亮的计划，然后跳过第三步直接做第五步。计划工具不会拒绝它，因为它压根没有拒绝的能力——它收到什么就存什么。harness 能看见跑偏，但不能阻止跑偏。

这个区分之所以重要，是因为可见性机制很容易被误当成约束机制。看到 harness 里存着一份带状态的计划，很自然会以为"顺序被管起来了"。没有。要真正强制顺序，需要一个能说"不"的东西——一个在动作发生前做检查、不满足就拒绝的环节。那是另一套机制（第 5 部分会讲到它在多执行者场景下的形态），和这份清单不是一回事。

这是"看见不等于强制"这条约束最干净的一个例子。在任何 agent 系统里，看到一个"让 harness 知道模型意图"的机制时，都该追问一句：它有拒绝权吗？

### 3.2 支线用干净上下文

agent 在修一个 bug。为了搞清楚一个函数被谁调用，它读了三十个文件，跑了二十条搜索命令。这些中间过程和"修好这个 bug"这个目标基本无关，但它们全都躺在主线程里，占着位置。

人遇到这种情况的做法是：另开一个终端去追，追完了关掉终端，只把结论记下来，回到原来的地方接着干。

agent 需要的是同一个能力。实现上它比听起来简单得多：**同一个循环，用一份全新的输入再进一次。**

具体地说，父循环调用一个委派工具，harness 构造一个只含有"请完成这件事"的干净输入，跑同一套循环逻辑，跑完之后只把最终的结论文本作为工具结果交回父循环。中间那几十轮对话历史整份丢弃。

需要明确的几个点：

**子执行者不是另一种 agent，也不是第二个模型。** 它跑的是同一套循环代码，用的可以是同一个模型。价值百分之百来自上下文边界，不来自"多了一个智能体"。这个认识很重要，因为它决定了你什么时候该用它——当且仅当某项工作会产生大量与主线无关的中间过程时。为了"让专门的 agent 做专门的事"而拆分，通常只是在增加成本。

**工具表要收窄。** 子执行者的工具里不能有委派工具，否则会出现不受控的递归嵌套。如果确实需要支持嵌套（有些场景需要），那必须有一个并发上限。

**丢掉的只是对话历史，不是副作用。** 子执行者在文件系统上做的事——创建的文件、跑过的命令——全都留在工作目录里。丢掉的只是注意力噪音。这个区分经常被搞混，导致有人以为委派出去的工作"不算数"。

**过境的东西必须被显式说出来。** 只有那段结论文本会穿过边界。子执行者看到的一切细节，父执行者一概不知道。这是这个机制的全部意义，也是它的全部风险——如果结论写得不够，父执行者会带着不完整的信息继续干活。所以给子执行者的任务描述里，"我需要你回答什么"必须写清楚。

代价也要说清楚：每一个执行者都在独立烧 token。委派一次的总成本高于不委派。它换来的是主线程的清洁度，而这个清洁度只有在任务足够长的时候才值回票价。短任务里委派是纯亏损。

### 3.3 知识分层：目录常驻，正文按需

项目里有一套组件规范、一份 SQL 风格指南、一套提交信息格式。你希望 agent 遵守它们。最直接的做法是全部拼进系统提示。

四千行系统提示，每一轮调用都带着。改一个 CSS 颜色也要带着 SQL 风格指南。绝大部分内容和当前任务无关，却在持续消耗预算，还把真正重要的指令稀释掉了。

人和文档打交道不是这样的。你不会把整个 wiki 背下来，你只知道"有这么一份规范"，用到的时候去翻。

把这个模式做成机制，需要把知识拆成两层：

**目录层**是每份知识的名字和一句话描述。这一层常驻在系统提示里，每份知识几个 token，总量可控。它的作用是让模型知道"存在这么一份东西，什么情况下该用"。

**正文层**是完整内容，几千 token。它不在系统提示里，而是在模型判断任务匹配时，通过一次工具调用注入进来——作为一条普通的工具结果进入历史。

这个设计的核心是**把一份成本从"每轮必付"变成了"用到才付"**。目录层的每轮开销是几十 token，正文层的开销只在实际相关的那些会话里发生。

几个实现细节值得记：

加载走注册表按名字查找，不走文件路径。给模型一个"读取这个路径的知识文件"的工具，等于开了一个路径遍历的口子。按名字查一张启动时扫描出来的表，这个口子不存在。

正文注入之后，它就是历史里的一条普通项，会跟着对话一路携带，直到被压缩掉或者会话结束。这意味着"按需加载"省的是"不需要它的那些会话"的钱，而不是"需要它的那次会话之后"的钱。

这一层和"项目常驻指令"是互补关系，不是替代关系。分界线很清楚：**永远适用的东西走常驻层**（这个项目怎么构建、提交信息用什么语气），**某类任务才用得上的东西走按需层**（怎么做代码审查、怎么写数据库迁移）。把按需知识焊进常驻层，就是回到四千行系统提示；把常驻约定做成按需加载，模型会在没意识到该加载的时候违反它们。

### 3.4 上下文压缩：有损，且必须提前

长会话的失败方式很固定：agent 读过几个大文件、跑过几十条命令，某一轮突然收到"输入超过最大上下文长度"，任务停在那里。能力没问题，工具没问题，是 harness 一直在往一个只增不减的序列里追加，直到 API 拒绝接收。

责任要归对位置。模型本身没有任何持久状态，它每一轮看到的"记忆"就是 harness 这次递过去的那段输入。所以"agent 忘了最初要干什么"和"agent 塞不进下一轮"是同一个问题的两面，都不是模型的缺陷，而是 harness 默认把"记住一切"当成了免费。最小循环里这个假设成立，因为会话短；任务一长就崩。

腾地方有四种想得到的做法：

**直接截断最早的若干轮。** 实现最简单，代价是任务目标通常就在最早那几轮里。用户最初说的"改完之后跑测试、不要动 lock 文件"被丢掉，agent 后面会理直气壮地违反它。截断把最重要的信息排在最先被删的位置，方向正好是反的。

**换一个更大窗口的模型。** 这不是解法，是把触发点往后推。窗口翻倍只是让崩溃发生在第八十轮而不是第四十轮，而且长输入本身会降低模型对中段内容的利用率，代价还要另付。真正无上限的会话必须有一个机制让历史不随轮数线性增长。

**把历史写进外部存储，按需检索。** 这条路在某些产品里是对的——跨天、跨会话、需要回答"三周前我们决定过什么"的场景。但它对当前这个问题是错的匹配：coding agent 的上下文里绝大部分是工具输出，彼此高度相关且时序敏感，检索出来的零散片段拼不成一个能接续工作的状态。而且它引入了一整套新东西（嵌入、索引、召回质量），而当前的需求只是"别超上限"。

**有损摘要。** 把旧历史交给模型总结成一小段，用这段替换原文。它承认信息会丢，但丢的方式是可控的：提示词可以指定优先保住什么。对"接着把活干完"这个目标，需要保住的东西很少也很明确——当前目标是什么、动过哪些文件、还有什么没做完。这几样恰好能压进几百个 token。这是四种做法里唯一在成本和保真度之间做出合理取舍的，也是主流实现的共同选择。

选定摘要之后，剩下三个细节全都必须定，任何一个定错都会出问题。

**一、什么时候压。** 闸门放在每次调用模型之前，而不是收到超长错误之后。理由是总结本身也是一次模型调用，它的输入是那一大段旧历史，也要装进同一个窗口。等窗口已经满了再压，这次总结请求也发不出去，agent 就彻底卡死了。所以触发阈值必须明显低于硬上限，留出足够空间装下总结请求本身。这是"提前压"的真正原因，不是性能优化。

判断"逼近上限"的依据，用估算还是精确计数？粗糙的字符数除以常数能跑，但它逼你把阈值设得很保守——估偏了就是卡死。生产实现拿 API 每次响应带回的真实用量来判断，阈值可以贴得近得多。**估算和精确计数的差别不在精度本身，在于它允许你把安全边际压到多小。**

![压缩的切分点](./assets/compaction-cut.svg)

**二、从哪里切。** 上下文是一个有序序列，其中工具调用和它的返回结果是成对出现的。如果切分点落在这两者中间，压缩之后模型会看到一个没有对应调用的悬空结果。

这个故障值得完整走一遍，因为它是典型的"症状离病因很远"。压缩发生在第三十轮，切在了第十二轮的一个工具调用和它的输出之间。压缩本身没报错，摘要也生成得好好的。下一次请求发出去，API 返回一个结构非法的错误，说某个输出项找不到对应的调用。这个错误信息里不会提到压缩，你看到的是第三十一轮的请求挂了。如果你的错误恢复逻辑把这类错误归进"未知错误，重试几次"，它会重试几次然后放弃，而每次重试都带着同一份坏掉的序列。真正的病因在十九轮之前的一次切分。

稳妥的切法是从后往前找最后一条用户消息，在它前面切。用户消息一定处在轮次边界上——一轮的定义就是从用户消息开始到模型不再调工具为止——所以这样切绝不会拆散任何一对调用与结果。当前这一轮原样保留，因为它正在被使用。

**三、摘要怎么生成。** 它是另一次模型调用，不是本地截断或正则抽取。这次调用的配置和干活那次完全不同：

| | 干活的调用 | 压缩的调用 |
|---|---|---|
| 目的 | 继续推进任务 | 把旧历史压成一段短文本 |
| 工具 | 带全套工具 | 不给工具 |
| 系统提示 | 你是 coding agent，动手别解释 | 写成几条要点，保住目标、动过的文件、未完成的工作 |
| 输入 | 当前上下文 | 被切掉的那段旧历史全文 |
| 输出 | 工具调用或最终回复 | 一段摘要 |

不给工具这一条是必要的，否则模型会在总结的时候开始干活。

压缩的账要算清楚，因为它直接决定阈值怎么设。贵的是输入：几乎整段旧历史要再读一遍。输出很短，基本不花钱。所以压缩是一次性支出，换来的是之后每一轮都不用再传那一大段原文。会话越长越划算；短会话里压缩纯属浪费，这说明阈值不该设得太低。手动触发和自动触发花的是同一种额度，区别只在谁按的按钮。

Codex 在这条路上的做法和上面一致。触发阈值是一个可配置的 token 数，还能选择这个阈值是按整段活动上下文算还是只算某个前缀之后的增量。它同时提供手动触发的压缩命令，走同一条总结-替换-继续的路径。有一个细节很能说明"自动和手动是同一条路"这件事被认真对待了：它的生命周期钩子里有"压缩前"和"压缩后"两个事件点，而这两个事件带一个标记区分本次是自动还是手动触发的——同一条路径，不同的触发源，钩子能看见区别。

它还在试一条替代路线：用可搜索的历史加笔记，代替反复把一切压成单一摘要。这条路承认了有损摘要的一个根本缺陷——压过三次之后，摘要的摘要的摘要已经什么都不剩了。值得关注，但目前不是主流。

最后要区分压缩和持久化的分工，这两件事经常被混在一起。压缩换的是窗口空间，代价是信息有损；它的产物活在内存里，进程一关连摘要都没了。持久化换的是寿命，记录精确无损，但它不解决窗口问题——一份完整的历史日志照样塞不进下一轮。两层都需要：活跃上下文里靠摘要接续工作，磁盘上靠精确日志恢复和分叉。

### 3.5 提示词组装与配置解析是两条路

![提示词组装与配置解析](./assets/prompt-vs-config.svg)

前面几节都在讲"往上下文里放什么"。这一节讲一个相邻但不同的问题：这些东西是怎么被决定的。

硬编码一行系统提示在最小实现里够用。agent 长大之后会撞上三件事：换个项目要重写整段提示，不知道哪些该改哪些该留；模型、推理档位、审批策略、沙箱模式全写死在源码里，想换个模型得改代码；项目自己的约定（提交信息用祈使句、收尾前先跑状态检查）没地方放，只能塞进 harness，一换项目就错。

问题不在提示词写得不好，在于 **harness 把"一段字符串"和"一组配置"混成了一件事**。它们是两条独立的路径，处理方式完全不同：

**文本合并**决定模型读到什么。内置的基础指令永远在最前面，声明身份和工具用法；项目级的约定文件存在就追加在后面。这条路的产物是一个字符串，直接进请求的指令字段。

**配置解析**决定这次调用是什么参数。用哪个模型、推理多深、审批档位、沙箱档位、后端指向谁。这条路的产物是一组取值，**它们不进提示词**。

把这两条路混在一起的典型症状，是有人把配置项的内容拼进系统提示——"当前沙箱模式是只读，请不要尝试写文件"。这句话是错的，不是因为它没用，而是因为它把一个硬约束降级成了一句建议。沙箱该拦的东西不需要告诉模型，模型该知道的边界应该通过工具调用被拒绝时的错误信息学到。**配置约束的执行不该依赖模型读懂了配置。**

文本合并这条路有一个细节值得看，因为它比"项目文件追加在后面"复杂：Codex 的项目级指令是逐目录收集的，从项目根一路走到当前工作目录，每一层最多取一个文件，然后从根往下依次拼接。这个顺序意味着**越靠近当前目录的约定出现在越后面，因此覆盖更上层的**。在一个 monorepo 里，根目录写"所有代码用 TypeScript"，某个子包写"这个包是 Python 的"，后者会赢。全局层还有一个优先级更高的覆盖文件名，存在就用它、不存在才用常规名——这是给"我想临时改掉全局约定又不想丢掉原文件"准备的。整份拼接还有一个字节上限，超了就停止追加。

配置解析这条路的核心是一条固定的优先级链。Codex 的链从高到低大致是：命令行参数和显式覆盖，项目级配置（仅限被标记为可信的项目，且从项目根向下越近越优先），选中的预设文件，用户级配置，系统级配置，内置默认值。

这条链的形状本身有几处值得学：

**项目级配置需要项目可信才生效。** 一个克隆下来的仓库带着配置文件进来，如果无条件生效，它可以把沙箱调到全放开。所以项目信任是一个前置条件。

**项目级配置有一个不能覆盖的键集合。** 即使项目可信，它也不能改模型后端指向、认证方式、遥测设置。这一条是"信任有边界"的具体落实：我信任这个仓库调整它自己的构建命令和代码风格，不代表我信任它把我的 API 流量导去别处。**设计配置层级时，一定要问哪些键是机器级的、不接受下层覆盖**，这个清单比层级顺序本身更重要。

**预设（profile）的存储形态变过。** 早期是主配置文件里的一个内联表，现在是独立文件，顶层的预设选择器也被去掉了。改动的理由不难推测：内联表会让主配置文件随预设数量膨胀，而且预设和根配置在同一个文件里，"这个键到底来自哪一层"的排查变得困难。拆成独立文件之后，每个预设自己是一份完整可读的配置。

调试这类系统时最有用的一个能力，是**对每个键报告它最终取值来自哪一层**。有几十个开关、四五层覆盖的配置系统，没有这个能力就只能靠猜。这不是锦上添花的功能，它应该和解析器一起设计。

## 第 4 部分 · 时间与寿命

上一部分处理的是空间：窗口里放什么。这一部分处理时间的三个不同侧面——会话能活多久、失败之后怎么走下一步、慢操作和定时任务怎么不把循环卡住。

### 4.1 会话是一等对象

到目前为止，那条输入序列一直只活在内存里。进程一关，会话就没了。

这带来三个具体的缺失。跑了一小时的长任务不能明天接着干。想回顾"它到底改过哪些文件"没有任何记录可查。想从某个中间状态岔一条分支试另一个思路，做不到。

责任还是在 harness 而不是模型。模型没有持久状态，所有记忆都在上下文里，上下文在内存里，内存随进程消失。**harness 从没把会话写到一个比进程更长寿的地方。**

写到哪里、以什么形式写，有三种候选：

**一个大 JSON 数组，每次更新整文件重写。** 直觉上最简单。问题有两个：写入成本随历史长度线性增长，一小时的会话每加一条消息都要重写几兆；更要命的是崩溃安全性——重写到一半进程挂了，文件里是一段截断的 JSON，整份会话都解析不出来。你丢的不是最后一条消息，是全部。

**关系数据库。** 有事务、有索引、能跨会话检索。但对本机单人 CLI 这个场景，它要求先跑一个数据库进程、管账号、做 schema 迁移，换来的并发能力和跨用户查询能力这里一个都用不上。还有一个容易忽略的问题：会话日志里常常有源代码和密钥，接一个远程库等于让这些东西默认出本机。

**只追加的行分隔日志。** 每产生一个项——用户消息、工具调用、工具输出、最终回复——就序列化成一行追加到文件末尾。

第三种是对的，理由可以对照着列：

| | 大 JSON 数组 | 只追加日志 |
|---|---|---|
| 新增一项的成本 | 重写整个文件，随历史增长 | 追加一行，恒定 |
| 写到一半崩溃 | 整份文件可能解析失败 | 已落盘的行完好，最多丢最后没写完的那行 |
| 看最新一条 | 必须整份解析 | 读最后一行 |
| 分叉 | 解析、复制、重新序列化 | 复制文件，换个头 |
| 人工审计 | 需要工具 | 直接用文本工具翻 |

**这个选择是被访问模式决定的，不是被"哪个技术更先进"决定的。** 这个场景的操作几乎只有五种：追加一行、整段按顺序读回、复制、移动、删除。全都是文件系统的原生操作。数据库提供的能力——事务、并发写、按任意字段检索、跨用户 JOIN——一个都没被用到。

反过来说，什么时候该换数据库？当访问模式变了的时候。产品变成多租户的云端服务，需要按人/按仓库/按时间检索，需要多机共享，需要接进组织的审计和备份体系——这时候日志文件的弱项（并发写不安全、跨会话检索只能扫文件）就成了主要矛盾。中间还有一档是本机的嵌入式数据库，仍是一个文件但带索引和事务，适合"在本机但要按字段查很多会话"。

**这是一个可迁移的判断框架：先列出实际的访问模式，再看哪种存储的原生操作和它对得上。**不要从存储技术的能力表倒着选。

写入时机上有一个决定：**项一产生就落盘，不等这一轮结束。**理由是崩溃可以发生在任何时刻，包括一轮的中间。等一轮结束再批量写，崩溃时丢的是整轮——而那一轮里可能已经改了十个文件。逐项写入让磁盘上的记录始终完整到最后一刻。

日志的第一行通常是一个头，记录会话 id、工作目录、启动时间等元信息。这个头的价值在恢复的时候体现：它让 harness 能精确重建会话的环境，而不是从对话内容里去猜。

Codex 的这些文件放在配置目录下按日期分层的会话目录里，文件名带时间戳和会话 id。归档的会话挪到另一个目录。这个布局本身也在说明前面那条判断——生命周期管理用的是目录操作。

### 4.2 会话的一生

![会话生命周期](./assets/session-lifecycle.svg)

会话能落盘之后，立刻出现一个新问题：会话会越攒越多。跑了两个月，几百条会话躺在目录里，其中大部分再也不会碰。

需要的是一个清晰的生命周期模型。有意思的是，一旦存储形态选对了，这个模型里的每个操作都变成了一次文件操作：

**继续。** 读日志，跳过头，按行解析成序列，接着跑。文件本身不动。

**分叉。** 复制成一个新 id 的文件，新头里记下从哪条会话岔出来的。**原会话一个字节都不动。**这一点是分叉和继续的核心区别，也是最容易被搞混的地方——分叉不是"从中间截断然后走另一条路"，是"复制一份，两条各自演化"。

**归档。** 挪进一个隐藏的目录，或者翻一个可见性标志位。**什么都没删。**默认的会话列表里看不到它，加上"显示全部"的选项还能看到。

**取消归档。** 挪回来。

**删除。** 这是唯一不可逆的操作，所以它应该是唯一需要显式确认的。

这五个操作，没有一个需要改动循环。它们全都是对磁盘上那份日志的增、删、移、复制。**一个设计得好的持久化层，会让生命周期管理自动变成一组文件操作；如果你发现生命周期管理需要在循环里加逻辑，说明存储形态选错了。**

有几个边界值得注意：

归档和删除必须在语义上和界面上都严格分开。用户归档一条会话的心理预期是"我以后可能还要看"，如果归档实际上删了数据，那是背叛预期。反过来，如果删除只是藏起来，用户以为清理掉的敏感会话其实还在磁盘上，这是安全问题。

会话的选择器默认按当前工作目录过滤——你在这个项目下，只想看这个项目的会话。但必须提供关掉过滤的选项，因为"我忘了当时在哪个目录跑的"是很常见的情况。

指定会话的参数需要同时支持 id 和名字，并且要有明确的消歧规则（比如能解析成 id 格式的就按 id，否则按名字）。这类"一个参数两种含义"的设计如果没有明确规则，会在名字恰好长得像 id 的时候出诡异的错。

### 4.3 失败是分类后的下一步

![错误分类与恢复路径](./assets/error-recovery.svg)

生产环境里 API 报错是常态，不是意外。限流、过载、上下文超长、用户按了取消键——这四种情况的正确反应完全不同，但最小实现里它们走同一条路：异常抛出，整轮崩溃。

把它们当成同一种"崩溃"，就像一辆车碰到减速带就熄火。需要的是一张"错误类型到恢复动作"的对照表，包在模型调用外面，循环形状不变。

| 类型 | 触发信号 | 恢复动作 | 明确不做的事 |
|---|---|---|---|
| 限流 / 过载 | 429、529，或消息里的对应关键词 | 带抖动的指数退避，重试有上限 | 立刻放弃；无上限重试 |
| 上下文超长 | 413，或"超过最大上下文长度"这类消息 | 压缩之后只再试一次 | 压缩失败后继续循环压 |
| 用户中止 | 取消信号 | 立刻停当前轮，会话保留 | 当成错误去重试 |
| 未知 | 其余 | 少量重试后放弃 | 和限流走同一条路径 |

有几个点需要展开。

**退避为什么要加抖动。** 纯指数退避是"等 0.5 秒、1 秒、2 秒、4 秒"。如果一群并发请求同时被限流，它们会在同一时刻一起重试，然后一起再被限流，形成同步的重试风暴。加一段随机抖动（比如在基准值上再加 0 到 25% 的随机量）就把它们打散了。这是分布式系统的常识，但在 agent harness 里经常被漏掉，因为单机开发时看不出来。

**压缩重试为什么只试一次。** 压缩是"腾出空间"的应急手段。如果压完了还是超长，说明问题不是"丢几条旧历史"能解决的——可能是单条工具输出就超过了窗口，也可能是摘要本身出了问题。这时候再压只会丢更多有效信息，而且很可能陷入"压缩、失败、再压缩"的死循环。用一个布尔标志限制成一次，失败就向上报，是正确的止损。

**用户中止为什么不是失败。** 重试一个用户主动取消的操作毫无意义。但更重要的是它的语义：中止的正确行为是"停掉当前正在跑的模型流和工具执行，但会话本身保留下来，用户可以立刻发下一条指令"。如果把它归进错误桶，会话可能被一起清掉，用户就得从头开始。**中止是一等的出口，和错误走完全不同的路。**

**这张表要包在哪一层。** 有两个选择，而生产实现通常两层都有。瞬时的 HTTP 错误（限流、服务端 5xx）的退避放在模型客户端层最合适——它对上层完全透明，上层看到的要么是成功的流，要么是"已经重试过 N 次仍然失败"。而上下文超长和用户中止必须放在轮次循环层，因为它们的恢复动作需要动上下文或者动会话状态，客户端层碰不到这些。

**工具执行失败和模型调用失败要分成两条路。** 审批拒绝、沙箱越界、工具名不存在、命令返回非零——这些走的是"把错误字符串作为工具结果喂回去"这条路，循环继续，模型自己决定下一步。模型调用抛错走的是上面这张分类表。把它们混在一起，会导致一条失败的 shell 命令触发退避重试，这既没用又浪费时间。

流式让"什么时候算失败"变得更细。连接可能在流中途断开，这时已经吐出来的内容可能已经足够（比如一个完整的工具调用已经收到了），也可能是残缺的。客户端需要判断能不能续上还是必须整轮重来。恢复哲学不变：先分类，再选代价最小的路径。

### 4.4 循环不阻塞：yield 窗口

![慢命令的 yield 与收割](./assets/yield-timeline.svg)

读一个文件是毫秒级的。装依赖、跑构建是分钟级的。同步执行把"发起调用"和"等到结束"绑成同一件事，于是慢命令一跑，整个循环卡在子进程上。而模型调用按 token 计费，空转的这几分钟是在纯烧钱。

解法的核心不是"做成异步"这么笼统，而是一个更精确的表述：**把"这一次工具调用最多等多久"和"这个进程要跑多久"解耦。**

具体做法是给工具调用一个 yield 窗口。发起命令，等待，直到进程结束或者窗口到期，两者取先。

窗口内结束了：这次工具调用的结果就是完整输出加退出码，跟同步执行没有任何区别。**快命令因此不需要模型处理任何额外概念**——这是这个设计最漂亮的地方。如果换成"立刻返回一个句柄，之后你自己去查"，那么读一个文件也要走两次调用，模型的每个简单操作都变复杂了。

窗口到期还在跑：返回一个会话句柄和"目前为止的输出"，同时标明"仍在运行"。模型拿到"仍在运行"之后可以去干别的事，后续某一轮再用这个句柄发起一次收割——等一个新的窗口，把上次切面之后的新输出取回来。

这里有个实现细节值得记：**要维护一个"已经给模型看过多少"的偏移量**。每次收割只返回增量，否则模型会反复读到同样的内容，既浪费窗口又让它困惑于"这条日志怎么出现了三次"。

现在说这一节里最重要的一条设计约束，它经常被违反：

**子进程的实时输出流不能自动灌进模型上下文。**

harness 通常会给客户端打一条事件流——命令开始了、有新输出了、命令结束了——终端界面靠它刷进度条。很自然会想：既然这条流已经有了，为什么不顺手推给模型？

不行，两个理由。一是量：一次构建的输出可能有几万行，全推进上下文会瞬间吃掉整个窗口。二是控制权：模型应该在它认为需要的时候主动去看进度，而不是被动地被进度淹没。**给界面的事件流和给模型的工具结果是两层东西，不该合并。**这是一条在很多地方都成立的原则——UI 事件不等于模型输入。

相关的一个决定：会话已经空闲时，后台进程结束了，该不该自动开一轮推理告诉模型"你那个构建跑完了"？

默认不该。理由是这会让 harness 在没有人要求的情况下烧一次模型调用，而且这次调用的上下文可能已经不相关了（用户早就换了话题）。事件停在客户端，模型要看到结果，得靠下一次收割、用户再说一句话，或者客户端显式地把完成消息交回来。把"完成后自动唤醒"做成默认行为，是一个看起来贴心实际上很吵的设计。

最后一个区分：教学实现里经常把快命令留在同步路径、只让慢命令走 yield，为的是让"拆开等待"这件事看得见。生产实现里命令一律异步，前台后台的区别只在这一次工具调用是等到结束还是 yield 之后再收。审批和沙箱对每一次落地执行同样生效，不因为它是后台的就放松。

### 4.5 闹钟在循环外面

定时任务是另一类时间问题。"每天早上九点跑一遍测试""每半小时看一眼仓库有没有新动静"，这些不该每次都要人来推一把。

最容易想到的做法是让循环自己看表——在每轮结束时检查有没有到期的任务。这条路错在两个地方：循环在跑一个长任务的时候不会回到检查点，定时就会漂移；而且它把"什么时候该跑"和"正在跑什么"耦合成了一件事，一个空闲的 agent 反而没机会检查。

正确的结构是三段，职责严格分开：

**调度器**是生产者。它按固定节奏醒来，扫描所有注册的任务，判断哪些到期了，把到期的放进队列。它从不亲自执行任何东西。

**队列**是解耦层。它的存在让调度器不必等 agent 跑完——调度器只管入队，入完就继续睡。

**派发器**是消费者。它在 agent 空闲时从队列取出任务，交进循环。

这个结构的价值在于**触发和执行之间有一个缓冲**。没有队列，调度器就得同步调用 agent，于是一个跑了十分钟的任务会让这十分钟里所有到期的任务全部错过。

派发这一步有一个实质性的选择，取决于这个定时任务的语义：

**开一张白纸。** 新建一条线程，把任务描述作为第一条用户消息。适合"每天跑一遍测试"这种彼此独立的任务——上一次的结果不该影响这一次。结果通常进一个收件箱等人看，没什么可报的就归档掉。

**追加回旧线程。** 把任务描述追加到某条已有的会话上，带着全部旧上下文继续。适合"盯着这个 PR，有动静告诉我"这种需要连续性的任务。

这两种语义差别很大，不能用一个机制硬套。前者要的是干净，后者要的是记忆。

还有几个工程细节：

**幂等标记。** 记录每个任务上次触发的时间点，同一个时间窗口内不重复触发。调度器的唤醒节奏和任务的时间粒度不可能完美对齐，没有这个标记就会出现同一分钟响两次。

**一次性任务要能注销。** 触发过就从注册表移除。

**日程的表达形式。** 五段式的 cron 表达式够用但表达力有限。日历标准里的重复规则（RFC 5545 的 RRULE）能表达"每月第二个周二""每个工作日"这类东西。Codex 的桌面应用存的是后者，界面上让你填 cron，存下来仍然转成 RRULE。

关于"闹钟在哪"，Codex 的形态很能说明分层：**开源 CLI 里没有调度器**，它只提供一个无头入口——给一个提示词，跑完一轮，把事件流打到标准输出，退出。本机想定时跑，是把系统的 cron、systemd 定时器或者 CI 接到这条命令上。真正内置闹钟的是桌面应用，任务定义落在配置目录下的文件里，调度状态存在本地数据库里。

这个分层是对的，值得抄：**无头入口是能力，调度器是产品。**把调度器塞进 CLI，等于要求 CLI 变成一个常驻进程，而那是完全不同的一类软件。提供一个干净的一次性入口，让外部的任何触发器都能接上去——系统定时器、CI、云端任务、邮件或聊天工具的事件——消费端一行不用改就能接新的事件源。

无人值守场景下审批策略基本只能是"从不问"，因为没有人可以问。这意味着命令要么在沙箱里跑通，要么直接失败。**自动化程度和权限收紧必须同步调整**：把审批关掉的同时不把沙箱收紧，等于给了一个无人监管的全权限进程。

### 4.6 无人值守：驱动方式与机器可读的出口

前面所有的讨论都隐含一个前提：有一个人坐在键盘前面，敲提示词、看进度、该批的时候批。

去掉这个人之后，同一个循环要面对三个新需求：让它读代码而不只是写代码；把它塞进脚本和 CI，然后程序化地消费结果；把任务委派出去让它在别处自己跑。

![触发源与出口](./assets/triggers-outlets.svg)

这三件事的共同点是：**循环本身一点问题都没有，问题是驱动方式和出口。**具体变的是三样东西——谁驱动它（人、脚本、CI、云端），它指向什么（一段对话、一个 diff、一个被委派的任务），结果怎么回来（终端输出、结构化事件流、一个 PR）。

**出口的形态是这里最实质的设计问题。**聊天文本对人友好，对脚本是灾难。脚本需要的是两样东西：

**一条结构化的事件流。**每一行一个 JSON 对象，描述会话开始、一轮开始、某个项完成、一轮结束（带 token 用量）、失败。项本身也有类型——命令执行、模型消息、推理、文件变更、外部工具调用、搜索、计划更新。有了这个，CI 里可以精确地知道 agent 做了什么，而不是从一段叙述里猜。

**一个受 schema 约束的最终结果。**这是比事件流更强的要求：让最终那条消息符合一份给定的 JSON schema。关键在于实现方式——不是生成完之后校验、不合格就重试，而是**在生成阶段就约束模型**，让它产不出不合 schema 的输出。这两种做法的可靠性差一个数量级，前者会在复杂 schema 上反复重试，后者是结构性保证。

还有一个很小但很重要的工程决定：**机器可读的输出走标准输出，人读的进度走标准错误。**这样 CI 里一条重定向就能把事件流存成文件，而人在终端看的时候两者仍然都在。这是 Unix 的老约定，但 agent 工具经常搞混。

"审查代码"这个形态特别值得单独看一眼，因为它展示了**同一个循环怎么通过换配置变成另一个产品**。它等于：换一份系统提示（你在审查，只报告问题，绝不修改文件）、在提示里塞一个 diff、挂一个输出 schema（整体判断加一组带文件、行号、严重程度的发现项）。执行路径本身完全复用无头入口，没有任何新代码。

这里有一个约束必须硬：**审查模式必须真的只读。**"只报告不修改"如果只写在提示词里，它就会在某些时候被违反——模型看到一个明显的 bug，顺手改了。正确的做法是配上只读的沙箱档位，让它物理上改不了。这是第 2 部分那条"不能接受被违反的规则不能只存在于提示词里"的一次具体应用。

至于跑在 CI 里，本质上没有新东西——就是在某个 runner 上跑那条无头命令。真正需要设计的是权限收紧：runner 上通常需要丢掉提权能力、限制到只读或者只能写工作区、把凭证通过 secret 注入而不是写进配置。

跑在云端的形态则是把隔离推到了另一个级别：每个任务一个独立的容器或微型虚拟机，克隆仓库，跑一段准备脚本装依赖注入密钥，agent 在里面自主干活，产物是一份 diff 或者一个 PR。这时候本机的沙箱档位就不重要了，因为整个环境本身就是可丢弃的。第 5 部分讲隔离级别的时候会回到这一点。

## 第 5 部分 · 多执行者

"重构整个后端"这种任务，一个上下文盖不住。窗口就那么大，改路由的时候认证模块的细节早被挤出去了。

多执行者是这个问题的解法，但它不是一件事，是四件互相独立的事被塞进了同一个名字里：注意力怎么隔离、信息怎么传递、顺序怎么保证、文件在哪写。它们需要四套不同的机制，混在一起想会设计出一团乱麻。

![多执行者的四层边界](./assets/multi-agent-boundaries.svg)

在展开之前先说一个前提：**多执行者默认是亏的。**每个执行者独立烧 token，总成本高于单个。它只在"任务确实能拆成互相独立的部分，且每部分都会产生大量中间过程"时才划算。主流产品的默认行为是只在用户明确要求并行时才派生，这个保守默认是对的。

### 5.1 注意力边界：各带上下文，信箱传信息

第 3 部分讲过的一次性委派，是最简单的形态：父循环发起，等到子循环结束，只回收一条结论。它能隔离一次跑偏，但扛不住三种需求——并行（父等着就没法同时跑第二个）、持续（子执行者交完结论就没了）、中途互传（研究者发现了写作者需要的东西，但要等全部结束才能交）。

放开这三条，需要的最小工具集是三件：

**派生，立刻返回。** 创建一个新执行者并给它初始任务，但**不等它跑完**。返回的是一个名字或者路径，用来后续寻址。这个"立刻返回"是相对一次性委派的核心升级，也是并行成为可能的前提。

**发信，排进对方的信箱。** 把一条消息放进目标执行者的收件队列。

**等待，阻塞到有更新。** 阻塞在自己的信箱上，直到有新消息或者超时。**超时是必须的**，否则一个死掉的对端会把等待方永久挂住。

每个执行者仍然是同一个循环，各自持有一份私有的输入序列。子执行者的工具表要收窄，至少不能有派生工具，否则会递归爆炸；如果确实支持嵌套，必须有并发上限。

现在说这一节的几个关键设计点。

**发信和"唤醒对方干活"必须分开。** 这是最容易设计错的地方。直觉上，发一条消息给一个空闲的执行者，应该让它醒过来处理。但这意味着任何一条消息——包括一句"我这边进展顺利"——都会触发一次完整的模型调用。成本上不可接受，行为上也很怪。

正确的做法是在消息上带一个标志位，区分"这条消息只是入队，你下次醒来时会看到"和"这条消息要求你立刻开始干活"。前者用于信息同步，后者用于派活。空闲的执行者只在收到后者时才启动新一轮。

**完成通知由 harness 投递，不是模型自己选一个工具说"我干完了"。** 理由是可靠性：如果靠模型调用一个"汇报完成"的工具，它会忘。让 harness 在子循环自然结束时（模型不再调用任何工具的那一刻）自动向父执行者的信箱投一条终态消息，这个通知就是必达的。

**信箱是进程内的通道，不是每个执行者一个磁盘文件。** 实现上就是一个队列加一个唤醒机制。这一点值得澄清，因为"给每个 agent 一个 inbox 文件"是一种很常见的想象，但那是另一种架构（通常出现在跨进程、跨机器的多智能体系统里），代价完全不同。会话历史走磁盘日志持久化，信箱本身随进程消失——这是合理的，因为未读消息在进程重启后本来就没有意义了。

**拓扑是树，通知一跳给父。** 子执行者完成时通知它的直接父节点，不会自动冒泡到祖父。这个约束让每个节点只需要关心自己的孩子。同辈之间可以直接通信，但编排职责通常还是留在根节点。

**过境的东西必须被显式说出来。** 这是整个机制的核心价值，也是它的全部风险。研究者可以读完几十份文档，只把一句结论发给写作者；根节点的窗口里可能只有两条终态消息。信息量的收缩是刻意的——但收缩得不够或者收缩错了，下游就拿着不完整的信息干活。

Codex 这套东西对应的是它的多执行者工具族，有派生、发送、等待、恢复、关闭这几个动作，寻址用的是类似路径的形式。投递给模型时会渲染一个明文的信封头，区分这是新任务、普通消息还是终态答复。工具名和具体形态在版本间变过（早期的等待语义是"等指定的孩子到终态"，后来改成"等信箱有更新"），但上面那几条设计约束是稳定的。

### 5.2 规则边界：能见度之外要有拒绝权

多个执行者要认同一份"谁先谁后"，就需要一个能拒绝非法开始的东西。

第 3 部分讲过，计划清单只有能见度没有约束力——模型可以跳步。单执行者场景下这是可接受的，因为跑偏至少是可见的，人能干预。多执行者场景下不行：三个执行者各自跳步，没有任何一个地方能看出全局顺序被破坏了。

要真正强制顺序，最小的机制是：

任务携带一个依赖集合。认领任务时检查依赖是否全部完成，不满足就**拒绝**。完成任务时扫描下游，把因此解锁的任务报告出来。

关键在那个"拒绝"。这是计划清单没有的东西，也是"看见"和"强制"的分界线。被拒绝的认领作为一条普通的工具结果回到上下文，执行者只能去认领别的任务。

把这些操作做成模型可调用的工具，而不是 harness 解析的特殊语法，有一个好处：操作的结果天然进入上下文，模型能基于板面状态继续推理。这和前面工具契约那一节是同一个道理。

这里必须说清楚一件事，免得你把它当成行业标准：**带依赖图的任务认领 API，在主流 coding agent 的源码里通常是不存在的。**它们有的是能见度清单，没有拒绝权。上面这套是一种把"顺序从自觉变成规则"讲清楚的实现方式，原则可迁移，具体 API 不是谁的标准。

真实产品里这个位置通常被别的东西填充：编排者（根节点）自己保证顺序，因为它是唯一派活的人；或者顺序被外部的工作流引擎管着；或者云端的调度层决定作业的执行次序。**共同点是顺序的裁决权在一个单一的地方，而不是分散在各个执行者的自觉里。**你可以选不同的实现，但不能没有这个地方。

### 5.3 并发带来的两个新问题

一旦真的并发起来，两个在串行世界里不存在的问题会冒出来。

**问题一：回执对不上账。**

根节点同时派出三份活，三条回复陆续回到它的信箱。它怎么知道哪条回复对应哪份请求？靠内容判断是不可靠的——三份活可能很相似，回复的措辞也可能雷同。

解法是标准的请求-响应关联：每条请求带一个 id，记进一本挂起账本；回复带上它要回答的那个 id；收到回复时按 id 勾账。**id 不在账本里的回复直接丢弃**，不要试图猜它属于谁——猜错比丢掉更糟。

要注意的是这本账和前面的信封头是两层不同的东西。信封头回答"这封信是什么性质、要不要让对方立刻开一轮"；请求 id 回答"它回答的是哪一次请求"。混在一起会设计出一个既管不好唤醒也管不好关联的字段。

同样要说清楚边界：**主流产品默认不需要这本账。**因为它们的默认编排模式是父节点一次关注一个（或少数几个）孩子，完成通知按执行者路径一跳投递，根本不存在 N 路请求对 N 路回执的场景。这本账是"真正并发派活"才需要的。如果你的设计里父节点总是等一个，就别加它。

**问题二：认领的竞态。**

如果把分配权下放——不是根节点派活，而是空闲的执行者自己扫描任务板去抢——那么两个执行者可能同时扫到同一个待办任务。

这是经典的 TOCTOU（检查时到使用时）竞态。它的结构是这样的：执行者 A 扫描，看到任务 1 空闲；执行者 B 同时扫描，也看到任务 1 空闲；A 认领，成功；B 认领，此时任务 1 已经被占了。

正确的处理不是"让扫描加锁"。扫描应该保持无锁且快，**它的结果本来就是一条线索，不是一个承诺。**唯一算数的检查必须在认领这一步的临界区里：拿锁，复查这个任务是不是真的还空着，是才置为进行中，然后放锁。

输的那一方要**诚实认输并去扫描别的任务**，而不是重试抢同一个。重试同一个会在高竞争下形成活锁。

跨进程的任务板，临界区换成数据库的条件更新（更新的 where 条件里带上"状态仍是待办"）或者比较交换操作，语义完全一样：**复查和置位必须是一个原子步骤。**

这一段同样要标清楚归属：**"空闲执行者自己抢活"在主流产品里不是默认模式。**它们默认是父节点推。云端的批量任务也是编排方按行推给执行槽，不是执行者来拉。自领模式是一种把临界区问题讲清楚的场景，原则（复查加置位必须原子）在任何共享状态的并发系统里都成立，但不要以为 agent 产品里普遍有一个"认领 API"。

还有一件真实调度器要处理而这里略过的事：执行者领了活之后崩溃，任务永远卡在"进行中"。生产系统需要租约超时、最大认领次数、完成事件落盘这些东西。提一句是为了让你知道这块冰山下面还有东西。

### 5.4 地盘边界：三个级别的隔离

![三个级别的隔离](./assets/isolation-levels.svg)

前三节解决了"谁干什么""按什么顺序""怎么传信息"，还剩一个问题没解决：**在哪干。**

两个执行者挤在同一个工作目录里，一个在改数据库层，一个在改 API 路由，两人都顺手动了同一个文件。写入互相覆盖，事后也分不清哪行属于哪份活。任务板和信箱对此毫无办法——它们管的是协调，不是文件系统。

隔离有三个级别，各自解决不同强度的问题，不能混为一谈：

| 级别 | 隔的是什么 | 共享什么 | 适用 |
|---|---|---|---|
| 工作目录隔离（git worktree） | 工作区目录 | 同一台机器、同一个内核、同一份仓库对象库 | 本机并行会话 |
| 沙箱 | 当前工作目录之外的一切 | 同一台机器、同一个文件系统 | 限制单个执行者的破坏半径 |
| 环境隔离（容器 / 微虚拟机） | 文件系统、进程、网络 | 只共享宿主的硬件 | 云端任务、不可信代码 |

**工作目录隔离**用 git 的 worktree 就够了：同一个仓库开出另一份工作目录，挂一条分支或者游离的 HEAD，共享同一份对象数据库。于是同一个路径可以以两份不同的内容同时躺在磁盘上。

这里有几个点要说准：

worktree 给的是"同一个仓库里的另一份目录"，不是"另一份仓库"。提交历史、对象库是共享的。

**真正的冲突不会消失，只是被推迟到交回那一刻**，由 git 诚实地暴露出来。这是它的特性不是缺陷——并行工作本来就会产生冲突，能做的是让冲突在一个明确的时刻、以一种可处理的形式出现，而不是以"文件被静默覆盖"的形式消失。

**工作目录是 harness 在会话启动时定的，模型没有"创建 worktree"这个工具。**循环开始之后模型只看得见自己那个目录。这个安排是对的：目录归属属于编排层的决定，不该让模型参与。

产品侧的出口通常是留着目录让人继续验、创建一条分支、交接回主工作区、或者开一个 PR。**自动合并进主分支不是产品行为。**演示用的自动合并只是为了把"推迟的冲突"演出来。

**沙箱和目录隔离是不同的事。**沙箱锁的是当前工作目录，所以两个 worktree 各自加上沙箱，天然就写不进对方的目录——这是沙箱的职责，不需要在 worktree 这一层再叠一次路径检查。反过来，沙箱本身不提供并行能力，它只是限制一个执行者的破坏半径。

**环境隔离是另一个量级。**worktree 仍然共享一台机器、一个内核、一份对象库；容器或微虚拟机把文件系统、进程、网络全部分开，产物是一份 diff 或一个 PR。它能容纳的风险级别完全不同——在可丢弃的环境里，本机那套沙箱档位就不重要了，因为整个环境本身就是笼子。

**这三级不要互相替代。**用 worktree 去解决"不信任这段代码"是错配（它还在你的机器上跑），用容器去解决"两个本机会话别互相覆盖"是过度设计（启动成本和调试成本都高一个量级）。

## 第 6 部分 · 能力外延与形态

### 6.1 外部能力走标准协议

把工具写进 harness 源码，意味着能力边界被焊在了发布节奏上。公司内部的工单系统、部署系统、知识库，不可能每一个都重写进 agent，更不可能每加一个就发一版。

需要的是一个标准协议：外部服务实现它，agent 就能调用，不管那服务用什么语言写、跑在哪台机器上。这条路上现行的协议是 MCP（Model Context Protocol）。

这一节的重点不是协议细节，是它的接入方式里有两个设计决定值得学。

**决定一：连接发生在循环开始之前，模型没有"连接"这个工具。**

直觉上可以给模型一个连接工具，让它在需要的时候去连。这条路错在几个地方：连接时机不可控，一个服务可能在会话进行到一半才被连上，而它的工具清单要在那时才出现在模型面前（很多模型接口不支持中途改工具表）；生命周期难管，谁负责断开、谁负责重连；而且这给了模型一个它不该有的决定权。

正确的做法是配置驱动的启动时发现：配置里声明每个服务器怎么启动，harness 在会话开始时把它们拉起来，握手，列出工具，把每个工具桥接成一个普通的函数工具。**对循环来说，桥过来的工具和内置工具长得一模一样**——一个名字、一份 schema、一次分发。循环不知道也不需要知道背后是另一个进程。

**决定二：给模型看的名字带命名空间，打给服务器的是原始名字。**

两个服务器都提供一个叫"搜索"的工具，不加区分就撞车了。所以模型看到的名字带服务器前缀（比如 `mcp__文档服务__搜索` 这种三段式），而真正发给子进程的调用用的是它自己的原始工具名。这是一个很小的翻译，但省掉了一整类"为什么调错了服务器"的问题。

真实实现里还要处理名字里的非法字符和长度上限——很多模型接口对工具名有格式和长度限制，而外部服务器的工具名不受你控制。

几个边界要说清楚：

**桥接不是提权。**破坏性的外部工具仍然要走审批。把一个操作包装成 MCP 工具，不会让它变得更安全。

**MCP 子进程不在沙箱里。**沙箱锁的是当前工作目录里那次落地执行，一个独立的子进程是另一条进程。不要把"我把它跑成子进程了"说成"我把它沙箱了"——这两件事完全无关。

传输通常至少支持两种：本地服务走标准输入输出按行收发，远程服务走 HTTP。后者会带出认证的问题（bearer token、OAuth），那是另一套东西，但不改变"启动时发现、按名调用"这条主干。

### 6.2 打包与钩子：能力注册在循环周围

按需加载的知识包、外部工具协议，都是"一次给 agent 加一样东西"。团队规模上来之后会撞上两个新需求。

**一个是分发。**一个团队想让所有成员拥有同一份规范、同一条防护检查、同一个外部服务连接。让每个人手动配三遍不现实。需要把它们打成一个包，一条命令装好。

这个机制本身不复杂：一份清单文件描述这个包里有什么，从某个源（本地路径、git 仓库、URL）安装。关键的设计点是**安装是叠加在默认发现之上，不是替换**。装一个包不应该让内置的东西消失，也不应该让另一个包的东西消失。这听起来理所当然，但如果实现成"读清单然后设置注册表"，就会互相覆盖。

**另一个是在循环的关键节点插自己的逻辑。**每次工具调用之前先过一道检查；每次调用之后记一条审计日志；会话开始时注入一段团队规约；一轮结束时发个通知。

这些都不是新工具，是挂在生命周期事件上的自定义命令。需要的事件点大致是这些类别：会话开始和结束、用户提交输入、工具调用前后、权限请求时、子执行者启动和停止、上下文压缩前后、一轮结束。

有两个设计点值得记：

**工具调用前的钩子要有阻断能力。**这是它和纯观测型钩子的根本区别。能阻断，它就是一道真正的策略层，团队可以用它实现自己的规则（比如禁止任何形式的强制推送），而不需要改 harness。不能阻断，它只是个日志器。相应地，被阻断的调用不会有对应的"调用后"钩子——工具压根没跑。

**钩子是来自配置的代码，所以它本身需要信任检查。**一个克隆下来的仓库可以带一段钩子进来，而钩子在工具调用前运行、有阻断能力、能执行任意命令。这就是为什么第 2 部分那条判定链的第一道闸是钩子信任——它必须排在最前面，因为它管的是"这段逻辑本身要不要执行"。

还有一个方向反转的形态值得一提：**把引擎自己暴露成一个外部服务。**不是 agent 去调别人，而是别的 agent 或者编排脚本把"跑一个任务"当成一次工具调用。这不改变循环，只是给它加了一个新的入口。

### 6.3 一个引擎，许多前端

![一个引擎，许多前端](./assets/engine-frontends.svg)

最后一个形态问题：同一个引擎要被很多种东西驱动——终端、编辑器扩展、桌面应用、远程终端、另一个 agent、托管的云服务。

如果每种形态重写一套 agent，那是维护灾难，而且行为会不一致。

正确的做法是把"循环加会话存储"做成一个引擎，前面架几种传输：进程内直连、某种 RPC 协议、外部工具协议。每种前端只是选了一条路进来。

这里的关键抽象是**会话标识**。引擎持有所有会话，每个有一个 id。开一条新会话返回 id，在某条会话上跑一轮需要指定 id。有了这个，一个前端开的会话可以被另一个前端接着跑——命令行开的会话，编辑器扩展可以续上。

有一个协议设计上的细节值得注意：**"开始新会话"和"继续已有会话"应该是同一个方法，只是参数不同。**给"跑一轮"和"续一轮"设计两个方法，会导致两条几乎一样的代码路径，然后它们慢慢分叉。

这一层的复杂度几乎全在传输和协议侧——方法集怎么设计、进度怎么流式推送、WebSocket 怎么鉴权、守护进程怎么配对、外部工具协议怎么握手。循环本身一行不改。

同时这也带来一个安全提醒：一旦引擎可以被网络驱动，第 2 部分那套判定链的重要性就上升了一个级别。本机终端里，人在现场；远程驱动下没有人在现场，审批弹给谁、沙箱按谁的策略配，都需要重新想一遍。

## 第 7 部分 · 合起来

### 7.1 一次落地执行的完整旅程

![一次落地执行的完整旅程](./assets/journey.svg)

前面二十五节都是局部。这一节把它们串成一条线：一次"改一个文件"的请求，从进来到结束，完整走一遍。

**进入。** 一条用户消息进来。它也可能来自定时器新开的线程、定时器追加回旧线程、或者某个执行者派生出来的干净输入——循环不区分。消息追加进那条唯一的输入序列，同时写进磁盘上的只追加日志。

**预算闸门。** 调模型之前先估当前序列的 token 量。假设这次超了预算：从后往前找最后一条用户消息作为切分点，把之前的历史交给一次没有工具的模型调用总结成一段摘要，用摘要项替换掉原文，保留当前轮。这次总结的输入很贵，但之后每轮都少传一大段。切分点落在用户消息之前，所以不会拆散任何一对工具调用与结果。

**指令组装。** 这次请求的指令字符串由内置基础指令加上逐层收集的项目约定拼成。模型是哪个、推理多深、审批哪一档、沙箱哪一档，来自另一条解析链，不进这个字符串。

**模型调用。** 外面包着错误分类。假设这次返回 429：按带抖动的指数退避等一会儿再试。第二次通了。

**追加与落盘。** 返回的整段输出——推理、要说的话、工具调用——原样追加进序列，同时逐项写进日志。一个字节都不改写。

**结构判据。** 这一轮里有工具调用，所以不收尾，进入分发。

**分发。** 按工具名查表。这次是一个补丁工具。它的身份决定了后面走哪条路：如果是计划工具，就只改 harness 内部状态然后直接返回，不进后面任何一道门；如果是派生工具，就起一个带自己输入序列的子循环；如果是慢命令，就走 yield 窗口；如果是外部协议桥过来的工具，就翻译成原始名字打给那个子进程。补丁工具会碰真实文件，所以它要过判定链。

**判定链。** 依次过：这个动作来源可信吗（不是钩子，跳过）；它依赖的能力开着吗（开着）；有没有设总旁路（没有）；沙箱放行吗——补丁要写的路径在工作目录内，放行；审批要问人吗——当前档位下写入需要确认，弹出审批，展示这份 diff，人批准了。如果配了额外的复审层或者这个项目被标记为不可信，这个"放行"还会被扳回"询问"。

**执行。** 补丁先在内存里算出每个文件的最终形态，全部校验通过才落盘。假设其中一个文件的上下文没匹配上：整个补丁被拒绝，磁盘一个字节没动，返回一条精确到文件和位置的错误。

**结果回写。** 无论成功还是失败，结果都作为一条普通的工具结果追加进序列，同时落盘。**失败不是异常出口，是数据。**

**回到开头。** 模型下一轮读到那条错误，重新读文件，产出一份修正过的补丁。这次匹配上了，落盘成功。

**收尾。** 再下一轮，模型不再调用任何工具。抽出最终文本，退出循环。会话仍然躺在磁盘上，明天可以继续，也可以从这里岔一条分支。

整条路上有一个贯穿始终的性质：**每一层说"不"的方式是一样的——写一条结果喂回去。**审批拒绝、沙箱越界、补丁不匹配、工具名不存在、依赖未满足、能力未开启，全都走这一条路。这个统一性不是巧合，是设计出来的，它让循环只需要处理一种失败形态。

### 7.2 三道接缝

![三道接缝](./assets/seams.svg)

把上面那条旅程压缩一下，会发现所有机制其实只挂在三个位置上，加上一类根本不在循环里的东西。

| 位置 | 在哪 | 挂着什么 | 特征 |
|---|---|---|---|
| 模型调用外套 | 发请求的前后 | 预算压缩、错误分类恢复、日志落盘、指令组装 | 不关心模型要做什么，只关心这次调用本身 |
| 分发外套 | 真正执行之前 | 判定链（信任、能力、旁路、沙箱、审批） | 关心这个动作会对世界做什么 |
| 注册表内侧 | 按名字找到的处理函数 | 命令、补丁、计划、知识加载、派生、协议桥 | 就是能力本身 |
| 循环之外 | 完全在外面 | 调度器、外部触发源、前端与传输、配置解析 | 它们把工作交进来或决定参数，但不在循环里 |

**加一个新机制的时候，先回答它属于哪一类。**这个归类练习的价值在于，它会立刻暴露设计错误：

归不进任何一类，通常意味着你要改循环。这时候该回头想想是不是把两件事混在了一起。

想挂在分发外套但需要知道工具的内部细节，说明工具的契约设计得不够结构化——判定链应该能从调用的声明里读出它要碰什么，不需要理解它的语义。

想挂在注册表内侧但需要拦别的工具，说明它其实是一道策略层，该挂在分发外套上。

想挂在模型调用外套但需要知道上一次工具执行的结果，说明它可能该是一个钩子事件而不是一层外套。

顺手记几个挂错位置的典型症状：**把策略写进提示词**（该在分发外套的东西被写成了给模型的建议）；**让模型自己声明安全性**（把判定权交给了被判定的一方）；**在循环里加条件分支**（本该是注册表里的一个条目或者一层外套）；**把调度器塞进循环**（本该在循环外）；**把界面事件流灌进模型上下文**（把两种不同用途的数据通道合并了）。

### 7.3 自检清单与反模式

最后回到开头那五条能力项，把它们变成可以拿去检查一个设计的问题。

**关于循环和状态**

- 停止判据是不是只依赖结构事实，不依赖对文本的理解？
- 那条输入序列是不是只增不改？有没有任何地方在裁剪或改写已经写进去的内容？
- 能不能在全景图上指出压缩、审批拒绝、沙箱越界、限流退避、慢命令 yield、定时触发各自发生在循环内还是循环外？说不清的那条路，线上就会在那里出事。

**关于工具**

- 加第二十个工具和加第二个工具，难度是不是差不多？
- 分发表里有没有混进权限判断？
- 每个工具的副作用落在哪（本机、服务端、外部目标），有没有对应的策略层管得住它？
- 失败返回的信息，够不够模型下一轮针对性修正？

**关于信任**

- "要不要问人"和"物理上碰得到什么"是不是两个独立配置的轴？
- 沙箱的强制力来自内核还是来自应用层的记得检查？
- 有没有任何一条不能接受被违反的规则，目前只存在于提示词里？
- 安全机制的叠加是不是单调收紧的？有没有哪个开关能放松另一个机制？
- 判定结果是三值（放行/询问/拒绝）还是被压成了两值？

**关于注意力**

- 常驻层是不是保持得足够短？
- 昂贵的知识是不是按需进历史，而不是每轮常驻？
- 压缩是不是在硬上限之前主动触发，而不是收到超长错误之后？
- 压缩的切分点会不会拆散工具调用与它的结果？
- 有没有把一个只有可见性的机制当成了约束机制？

**关于寿命与时间**

- 崩溃发生在任意时刻，磁盘上的记录是否完整到最后一刻？
- 归档和删除在语义上和界面上是否严格分开？
- 错误有没有分类？还是所有失败走同一条路？
- 用户中止是不是被当成了一种错误去重试？
- 慢命令会不会阻塞推理？界面事件流有没有偷偷灌进模型上下文？
- 定时逻辑是不是长在循环内部？

**关于多执行者**

- 主线程里有没有出现支线的中间过程？
- 过境的信息是不是被显式发送的？
- 完成通知有没有明确的投递对象，还是靠模型记得汇报？
- 并行写入有没有各自独立的地盘？
- 顺序的裁决权在一个单一的地方，还是分散在各个执行者的自觉里？
- 共享状态的认领，复查和置位是不是一个原子步骤？
- 用的隔离级别和要防的风险级别是否匹配？

**关于外延**

- 加一个外部能力是改配置还是改源码？
- 桥接过来的工具有没有被当成"已经安全"而跳过判定链？
- 多个前端是共用一个引擎和一份会话存储，还是各写了一套？

最后一条，也是最容易被忽略的一条：**你记住的应该是这些轴上有哪些语义位置，而不是某一版实现里它们叫什么名字。**这份笔记里出现的几处版本漂移——审批档位从四个收敛到两个加一种细粒度形态、Linux 沙箱后端从一种内核机制换成另一种、预设配置从内联表变成独立文件、线路协议从两种砍到一种——每一处都说明同一件事：**枚举值和键名是当期的工程折中，会变；而"为什么需要这条轴""它的两端各是什么"不会变。**

能在一个陌生的 agent 系统里指出它的那条循环在哪、状态源是什么、机制挂在哪几道接缝上、哪些边界是硬的哪些是软的——这个能力比记住任何一套 API 都管用。
